# EcoPower Logistics API

A REST API for EcoPower Logistics, the case-study company for Project 2 of CMPG323 (IT Developments) at
North-West University, 2023. EcoPower Logistics delivers and installs solar energy systems. The API keeps
its customers, products, orders and order lines, and exposes create, read, update and delete over each of
them.

It is an ASP.NET Core 6 Web API: ASP.NET Core Identity for accounts, JWT bearer tokens in front of every
data endpoint, EF Core 6 on SQL Server for storage, and a Swagger UI for trying it out. It ran on Azure App
Service with an Azure SQL database for the module; both have since been retired, so today it runs locally.
It is a university project and reads like one: scaffolded controllers, no tests, and a database name with a
typo that stuck.

## Features

### Accounts and tokens (`AuthenticateController`)

- **Register** with a username, an email address and a password (`POST /api/Authenticate/register`).
  Usernames must be unique; the email is validated as an address.
- **Register an admin** the same way (`POST /api/Authenticate/register-admin`). This creates the `Admin`
  and `User` roles if they do not exist yet and puts the new account in `Admin`.
- **Log in** (`POST /api/Authenticate/login`) and get back `{ token, expiration }`. The token is an
  HMAC-SHA256 JWT carrying the username, a `jti` and one role claim per role the account holds. It expires
  3 hours after it was issued. A wrong username or password returns `401`.

### Business data (`Customers`, `Products`, `Orders`, `OrderDetails`)

- The same five operations on each: list all, get one by id, create, replace, delete.
- `POST` returns `201 Created` with a `Location` header. `PUT` and `DELETE` return `204 No Content`. An
  unknown id returns `404`.
- Ids are supplied by the caller (`short`, never generated by the database). A `PUT` whose body id differs
  from the URL returns `400`. A `POST` with an id that is already taken returns `409 Conflict`.
- The model: a customer has many orders, an order has many order lines, and each line points at one
  product.

### Security

- Every data endpoint sits behind `[Authorize]`, so it needs a valid bearer token. Only the three
  `Authenticate` endpoints are open.
- Tokens are validated for issuer, audience, lifetime and signature.
- HTTP requests are redirected to HTTPS.

### Documentation

- Swagger UI with an **Authorize** button. The Bearer scheme is applied to every operation, so each one
  shows the lock icon.

## Getting started

### Prerequisites

- [.NET 6 SDK](https://dotnet.microsoft.com/download/dotnet/6.0)
- [SQL Server LocalDB](https://learn.microsoft.com/sql/database-engine/configure-windows/sql-server-express-localdb)
  (installed with Visual Studio), or any SQL Server you can point a connection string at
- The [EF Core CLI](https://learn.microsoft.com/ef/core/cli/dotnet): `dotnet tool install --global dotnet-ef`

### Running locally

No secrets are stored in this repository. In Development they come from
[user secrets](https://learn.microsoft.com/aspnet/core/security/app-secrets); anywhere else, use environment
variables or App Service settings. `Program.cs` refuses to start, and names the missing key, if either
setting in step 1 is absent. That includes the EF Core CLI's design-time start, so step 1 must come before
step 2.

```bash
git clone https://github.com/Robotbino/CMPG323-Project-2-37687638.git
cd CMPG323-Project-2-37687638
```

1. Set the two required settings from the project folder (PowerShell):
   ```powershell
   dotnet user-secrets set "ConnectionStrings:ConnStr" "Server=(localdb)\MSSQLLocalDB;Database=Poject2;Trusted_Connection=True;MultipleActiveResultSets=true"
   $bytes = New-Object byte[] 32; [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($bytes)
   dotnet user-secrets set "JWT:Secret" ([Convert]::ToBase64String($bytes))
   ```
2. Create the database. The Identity tables already have a migration
   (`Migrations/20230831102711_Initial.cs`). The business tables (customers, orders, order details,
   products) were scaffolded from the original Azure database, so generate their migration once:
   ```powershell
   dotnet ef database update --context ApplicationDbContext
   dotnet ef migrations add BusinessSchema --context Poject2Context --output-dir Migrations/Poject2
   dotnet ef database update --context Poject2Context
   ```
3. Start the API with `dotnet run` and open **https://localhost:7142/swagger**.
   `Properties/launchSettings.json` binds `https://localhost:7142` and `http://localhost:5142`, sets
   `ASPNETCORE_ENVIRONMENT=Development`, and opens `/swagger`. The HTTP port redirects to HTTPS.
4. Register with `POST /api/Authenticate/register` (or `register-admin`) and log in with
   `POST /api/Authenticate/login`. Then click **Authorize** and enter `Bearer <token>`: every Customers,
   Orders, OrderDetails and Products endpoint requires it.

### Configuration

| Key | Supplied by | Used for |
|---|---|---|
| `ConnectionStrings:ConnStr` | User secrets in Development; the environment variable `ConnectionStrings__ConnStr` or an App Service setting elsewhere | The SQL Server connection for both `DbContext`s |
| `JWT:Secret` | User secrets; `JWT__Secret` or an App Service setting elsewhere | The HMAC-SHA256 key. `AuthenticateController` signs with it; `Program.cs` validates with it |
| `JWT:ValidIssuer` | `appsettings.json` (`http://localhost:61955`) | Written into every token as the issuer and required by the validator |
| `JWT:ValidAudience` | `appsettings.json` (`http://localhost:4200`) | Written into every token as the audience and required by the validator |
| `JWT:Issuer`, `JWT:Audience` | `appsettings.json` | Not read anywhere |

The issuer and audience are plain strings compared between the controller that mints tokens and the
middleware that validates them, so they do not have to match the address the API listens on.

## API

Every controller is routed as `api/[controller]`. Routes are case-insensitive.

### Endpoints

**Accounts** (open, no token needed)

| Method and route | Body | Result |
|---|---|---|
| `POST /api/Authenticate/register` | `{ Username, Email, Password }` | `200` with `{ Status: "Success", Message }`. `500` with `Status: "Error"` if the username exists or creation fails |
| `POST /api/Authenticate/register-admin` | `{ Username, Email, Password }` | As above, and the account is added to the `Admin` role |
| `POST /api/Authenticate/login` | `{ Username, Password }` | `200` with `{ token, expiration }`, or `401` |

**Business data** (every route requires `Authorization: Bearer <token>`)

| Resource | `GET` | `GET {id}` | `POST` | `PUT {id}` | `DELETE {id}` |
|---|---|---|---|---|---|
| `/api/Customers` | list | one | create | replace | delete |
| `/api/Products` | list | one | create | replace | delete |
| `/api/Orders` | list | one | create | replace | delete |
| `/api/OrderDetails` | list | one | create | replace | delete |

Status codes are the ASP.NET Core scaffold's: `200` for reads, `201` for create, `204` for replace and
delete, `404` for an unknown id, `400` when a `PUT` body id does not match the URL, `409` when a `POST` id is
already taken.

Request and response bodies are the entities in `Models/`:

| Entity | Fields |
|---|---|
| `Customer` | `CustomerId` (short), `CustomerTitle`, `CustomerName`, `CustomerSurname`, `CellPhone` (strings, max 50) |
| `Product` | `ProductId` (short), `ProductName` (required, max 50), `ProductDescription` (max 50), `UnitsInStock` (int) |
| `Order` | `OrderId` (short), `OrderDate` (datetime), `CustomerId` (short), `DeliveryAddress` (max 50) |
| `OrderDetail` | `OrderDetailsId` (short), `OrderId` (short), `ProductId` (short), `Quantity` (int), `Discount` (int) |

### Authentication

- Accounts are ASP.NET Core Identity: `ApplicationUser : IdentityUser` and `IdentityRole`, stored by
  EF Core through `ApplicationDbContext`, with the default token providers.
- Two roles, `Admin` and `User` (`Authentication/UserRoles.cs`). `register-admin` creates both roles if
  they are missing and assigns `Admin`. `register` assigns no role.
- `login` finds the account by username and checks the password with `UserManager`. It then issues a
  `JwtSecurityToken` with these claims: the username (`ClaimTypes.Name`), a new GUID as `jti`, and one
  `ClaimTypes.Role` claim per role. Issuer is `JWT:ValidIssuer`, audience is `JWT:ValidAudience`, expiry is
  `DateTime.Now.AddHours(3)`, and the signature is HMAC-SHA256 over `JWT:Secret`. The response echoes
  the expiry as `expiration`.
- `Program.cs` makes JWT bearer the default authenticate, challenge and scheme. Validation checks issuer,
  audience, lifetime and the symmetric key. `RequireHttpsMetadata` is off and `SaveToken` is on.
- `[Authorize]` on the four data controllers requires a valid token and nothing more. No endpoint checks a
  role.

### Swagger

- **Development** (`dotnet run`, Visual Studio): the document is at `/swagger/v1/swagger.json` and the UI
  at `/swagger`.
- **Any other environment** (how it ran on Azure): the same document, with the UI served at the site root
  `/` (`RoutePrefix = ""`).
- The document is titled `API v1`. The security definition is an `ApiKey`-type header named
  `Authorization`, which is why you type `Bearer <token>` yourself in the Authorize dialog.

## How it works

- **Two `DbContext`s, one connection string.** `ApplicationDbContext` owns the `AspNet*` Identity tables
  and `Poject2Context` owns the four business tables. `Program.cs` registers both with
  `UseSqlServer(connectionString)`, so they share one database. `Poject2Context` also has an
  `OnConfiguring` fallback, `UseSqlServer("Name=ConnectionStrings:ConnStr")`, that resolves the same key
  when the context is built without options.
- **Database-first business model.** `Poject2Context` and the four entities are EF Core scaffolds
  (`partial` classes, `OnModelCreatingPartial`) from the original database. All four keys are
  `ValueGeneratedNever()`, string columns are capped at 50 characters, `OrderDate` is SQL `datetime`, and
  the foreign keys keep their database names (`FK_Orders_Customers`, `FK_OrderDetails_Orders`,
  `FK_OrderDetails_Products1`) with `ClientSetNull` delete behaviour.
- **Startup fails loudly.** `Program.cs` reads `ConnectionStrings:ConnStr` and `JWT:Secret` before it
  registers anything. A missing one throws `InvalidOperationException` naming the key.
- **Pipeline.** Swagger, then HTTPS redirection, authentication, authorisation, controllers. There is no
  CORS middleware.
- **Two namespace roots.** The authentication code lives in `JWTAuthentication.*`, everything else in
  `CMPG323_Project2_37687638.*`. `Program.cs` imports both.

## Known limitations

- **No tests and no CI.**
- **The business schema has no migration in the repo.** `Poject2Context` was scaffolded from the existing
  Azure database, so only the Identity tables (`ApplicationDbContext`) have one. Step 2 of
  [Getting started](#getting-started) generates the business migration locally.
- **University-project scope.** The four data controllers are the ASP.NET Core scaffold: no paging, no
  filtering, no DTOs, and no validation beyond the model types. `PUT` replaces the whole row.
- **Ids are chosen by the caller.** All four keys are `short` and `ValueGeneratedNever()`, so a clash on
  `POST` is a `409`.
- **Roles are issued but never enforced.** No endpoint uses `[Authorize(Roles = ...)]`. `register`
  assigns no role, and the `User` role is only ever created (by `register-admin`), never assigned, so no
  token carries a `User` role claim.
- **Register errors are `500`s.** A duplicate username and a failed creation both return `500` with a
  `{ Status: "Error", Message }` body rather than `400` or `409`.
- **No CORS policy**, so a browser app on another origin cannot call it.
- **Tokens last 3 hours and there is no refresh.** Log in again.
- **Config leftovers.** `JWT:Issuer` and `JWT:Audience` in `appsettings.json` are unused, the Swagger
  document is titled `API`, and the `.csproj` still references the ASP.NET Core 2.2-era
  `Microsoft.AspNetCore.Identity` package next to the 6.0.21 one.
- **`Poject2`.** The database, its context and the Azure resources were named `Poject2`, a typo of
  `Project2`. It stays because the scaffold and the connection string use it.
- **No live deployment.**
